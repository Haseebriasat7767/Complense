# ComplyLens AI

**Know what's missing before the auditor does.**

ComplyLens AI is a demo-first compliance readiness workspace. You upload the evidence your team already has, it maps that evidence to SOC 2 and ISO/IEC 27001 controls, shows you exactly which controls are missing or only partially covered, ranks the resulting gaps by risk with a suggested fix/owner/timeline, and produces a branded PDF readiness report.

It runs end to end with **zero API keys, zero paid services and zero configuration**: `npm install && npm run dev`.

> **Read this first.** ComplyLens AI produces a *preliminary readiness assessment* from the evidence you provide. It is **not** a certification body, an auditor, an audit opinion, a legal service, or a substitute for professional compliance advice. Nothing in this repository claims that any organisation is SOC 2 certified or ISO 27001 certified.

## What it does

1. **Upload evidence** — PDF, DOCX, TXT or CSV, up to 10 MB, validated server-side. Eight named sample documents ship with the demo workspace.
2. **Analyse the text** — each document is classified, summarised and matched against the evidence each control expects.
3. **Map evidence to controls** — you see which controls the document supports, with a confidence score and the specific items found and missing.
4. **Detect gaps** — every control that is not fully evidenced becomes a finding, ranked Critical → Low and P1 → P4.
5. **Plan remediation** — each finding carries a recommended fix, a suggested owner and a suggested timeline, labelled as generated guidance.
6. **Report readiness** — generate a PDF readiness assessment (cover page + twelve numbered sections) for a framework and download it from the browser.

## How the analysis works

There is no black box and no randomness. The same evidence always produces the same assessment.

- **Matching** — each control lists the evidence items it expects, each with literal signal phrases. An `analyzed` document satisfies an item when a signal is present in its extracted text. Documents flagged `needs_review` only register a weak mention (they never close a control) and `failed` documents are excluded entirely.
- **Status** — coverage of a control's required items: `≥ 75%` **passed**, `≥ 30%` **needs attention**, else **missing**; documents awaiting manual review leave a control in **needs review**.
- **Confidence** — `0.65 × item coverage + 0.35 × signal strength` (floored at 0.05); evidence→control mapping confidence is `0.6 × coverage + 0.4 × depth`, halved for unverified documents.
- **Readiness index** — a transparent weighted composite: control health 28%, evidence coverage 35%, evidence depth 12%, remediation planning 25%. Partial controls earn 70% credit. Bands: ≥ 85 strong, ≥ 70 moderate, ≥ 50 at risk, below that critical.
- **Findings** — `missing` escalates the control's inherent risk one level, `needs attention` keeps it, `needs review` reduces it by one. Priorities follow from the resulting risk level.

Worked example from the demo workspace: `SOC2-CC6.1` (logical access) is **needs attention / high** because the Access Control Policy is present but no quarterly access-review or provisioning evidence exists, so the recommendation is to document and run quarterly user-access reviews and retain the reviewer, population and outcome — owner *Security / IT*, 30 days.

Details: [`docs/AI-ABSTRACTION.md`](docs/AI-ABSTRACTION.md) and [`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md).

## Deployment

Two verified shapes, both keeping the client and API on **one origin** (no CORS, one URL, no second service):

**A — one Node service** (default; Railway, Render, Fly.io, a VPS, Docker, any container host):

```bash
npm ci
npm run build          # client -> client/dist, server -> server/dist
NODE_ENV=production SESSION_SECRET="<long-random-string>" npm start
```

**C — Vercel** (one public URL, almost zero configuration): Vercel serves `client/dist` from its CDN and routes `/api/*` to a single function that runs the *same* Express app (`api/index.mjs`); `vercel.json` holds the build, rewrites, SPA fallback and headers. Import the repo, optionally set `SESSION_SECRET`, deploy.

```bash
npm run build && npm run verify:deploy   # verifies the Vercel shape end to end locally
```

Health check: `GET /api/health` → `{"status":"ok", ...}`.

On Vercel the default upload limit becomes 4 MB (the platform's request-body ceiling) and the in-memory store is per instance — set `MONGODB_URI` to persist. For a split deployment (static client on Vercel, API elsewhere) build with `VITE_API_BASE_URL=https://api.example.com` and set `CORS_ORIGINS` on the API. Step-by-step instructions, environment tables and troubleshooting: [`docs/DEPLOYMENT.md`](docs/DEPLOYMENT.md).

## Security summary

- Sessions: HS256 JWT, `SESSION_SECRET` from the environment, expiry enforced server-side; passwords hashed with scrypt.
- Authorisation: every evidence, control, gap, report and settings query is scoped to the caller's organisation; settings writes are limited to owners/admins.
- Uploads: extension and size validated server-side, parsed in memory only, never written to disk; the extracted text is what gets stored/analysed.
- Input: request bodies validated in helpers; errors are returned as `{ error: { code, message } }` without stack traces or internal details.
- Frontend: no secrets in the bundle — the client only ever talks to its own `/api`.
- Rate limiting: fixed-window limiter on `/api` (600 requests/minute per IP, 30 per 10 minutes on auth endpoints), plus baseline security headers.
- Session tokens are validated defensively: a missing, malformed, expired or wrongly-signed token returns `401` (never a `500`) and the client clears the stored session on any `401`.
- Password reset cannot be used to enumerate accounts: known and unknown addresses receive a byte-identical response.

Full detail, including what this demo deliberately does **not** implement (SSO, MFA enforcement, encryption at rest, audit-log export), is in [`docs/SECURITY.md`](docs/SECURITY.md).

## Known limitations

- The demo store is **in-memory**: restarting the server resets uploads, generated reports and settings changes. Set `MONGODB_URI` to persist them. On a serverless host (Vercel) each instance keeps its own copy until it is recycled, so demo figures stay deterministic but user uploads are per instance.
- Uploads are limited to 10 MB in a container deployment and 4 MB on Vercel (platform request-body ceiling). The UI reads the effective limit from the API.
- PDF/DOCX extraction is a lightweight in-memory scan: documents without a reliable text layer are marked **needs review** (or **failed**) instead of being guessed at. OCR is roadmap work, not present.
- The report is a readiness assessment snapshot, not a certification, audit opinion or control-attestation report (no SOC 2 §4 opinion language, no ISO certification claims).
- Notifications and billing are UI-only in this build: preferences are stored, no email or payment provider is connected.
- The rate limiter is per-process; a multi-instance deployment needs a shared store.
- The control library is a curated demo subset (50 controls across 14 categories), not the full criteria/Annex A text and not a licensed copy of any standard.
